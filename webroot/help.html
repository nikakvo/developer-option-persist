1 · what this module does

Turning Developer Options off in Android's Settings also turns off everything inside it — USB debugging goes with it. This module keeps the switches you care about in the state you chose, while Developer Options themselves stay hidden from the Settings menu.

The result: the developer menu is not visible, but ADB keeps working.

A background daemon watches for anything that changes those values — you, an app, an OTA, a settings reset — and puts them back.
Tested on a Poco F6 Pro with the Xiaomi.eu ROM (HyperOS 3, Android 16) and SukiSU-Ultra only. Other devices and ROMs may behave differently — the Xiaomi-specific settings in particular. If the header shows poll engine, change detection fell back to timed checks on your ROM.

The inverted one

Developer Options is the only toggle whose switch means hidden. Green means the menu is hidden from Settings — which is the point of the module. The runtime table shows the raw value, where 0 is hidden.

Mock location app

The app Android lets fake your location — what Developer Options calls Select mock location app. It is not a setting but an AppOp: the chosen app gets allow, every other one deny, exactly as Settings does it. Picking the app in this interface is the same as picking it in Developer Options, and works while they are hidden.

The picker lists every installed app that asks for the mock location permission, whether or not it has ever been selected, so a newly installed app shows up on its own. It is not managed by default.

Xiaomi-specific

The last three exist on Xiaomi / HyperOS. On another manufacturer they either do nothing or never appear, and the runtime table will show a permanent drift. Set them to skip and the daemon will leave them alone.

3 · how enforcement works

A daemon like this could poll every few seconds and re-read everything. Early versions did, and it cost roughly a million process spawns per day — enough to keep the CPU from settling into deep sleep. Since v6 the daemon does not poll at all: it waits for the system to tell it that something changed.

The event engine

Android saves settings by writing settings_global.xml.new or settings_secure.xml.new and renaming it into place, and init does the same with /data/property/persistent_properties whenever a persist.* property changes. One busybox inotifyd watches those directories, plus the module's own data directory for config changes.

The mock location app is kept in /data/system/appops_accesses.xml, which Android saves the same way about ten seconds after a change, and /data/system/packages.xml moves whenever an app is installed, updated or removed. Both are watched too; that directory is otherwise quiet.

The daemon reads those events with the shell's built-in read. Waiting, filtering and keeping time are all builtins, so while nothing happens the daemon starts no processes at all.

Only what changed

An event names the file that changed, and the daemon checks only the keys that live there: a change to the global settings checks USB Debugging and Developer Options, a property change checks the two Xiaomi properties, an AppOps or package change checks the mock location app, and so on.

Cooldowns

HyperOS rewrites settings_secure.xml every few seconds for unrelated reasons. Checks of that file are therefore rate-limited by the profile, while the quiet sources — global settings and properties — are checked within a second or two. A cooldown only delays a check; it never skips one.

Safety net

A full verification of every key still runs on a long timer, in case an event is ever missed. If the watcher process dies it is restarted automatically; if it keeps dying, the daemon switches to the poll engine by itself.

The poll engine

Without inotifyd, or with the engine set to poll, the daemon wakes on a timer, compares the modification times of the same files with one stat, and checks only the sources that changed.

Idle cost with the event engine: zero process spawns, and no write to module.prop unless the status text actually changes.
4 · profiles & battery
profileglobal / propssecurefull checkpoll tick
fast1 s2 s5 min15 s
balanced1 s10 s15 min60 s
battery2 s30 s30 min5 min

The first two columns are how soon a change is undone with the event engine. The last one applies only to the poll engine.

Balanced is the default and the right answer for almost everyone. With the event engine the profile mainly decides how often the noisy secure settings are looked at; an idle daemon costs nothing in any profile.

Profile and engine changes take effect immediately — the daemon is told about them and does not need a restart.
5 · the interface

Header

The version comes from module.prop; next to it is the engine that is actually running: event engine, poll engine or not running.

Status bar

  • enforcing — daemon alive, every managed value matches
  • drift detected — daemon alive, something does not match yet
  • paused — original values were restored; nothing is enforced until Apply Now or the next reboot
  • daemon stopped — nothing is being enforced

Below it: the daemon's PID, the watcher's PID, uptime and the last correction. Liveness is read from /proc, and a PID only counts if its command line really is this module's daemon.

Settings cards

The switch is what the config asks for. The badge under the name is what the system reports right now — green when they match, amber when they do not.

Mock Location App card

The picker offers not managed plus every installed app that asks for the mock location permission. The list comes from a cache. When apps have been installed, updated or removed, only those are checked again, in the background, and the picker fills in when that is done. The very first scan checks every user app and takes a few seconds. The badge shows which app actually holds the permission. If the chosen app is uninstalled, Android drops its permission and the module switches the setting back to not managed on its own.

Runtime table

Per setting: config value, live value, and whether they match. unmanaged means the key is set to skip; n/a means the settings service did not answer.

Actions

  • Apply Now — enforce immediately, and start the daemon if it is not running
  • Restart Daemon — stop and start it
  • Restore Original — put back the values from before installation and pause enforcement

Tuning

Profile and Engine (auto = events, poll = timed checks) show what they currently mean underneath. Log Level 2 adds debug lines such as config reloads and full verifications.

6 · configuration file

/data/adb/dev-options-persist/config — outside the module directory, so it survives module updates.

# 1 = force on, 0 = force off, skip = leave this setting alone
adb_enabled=1
development_settings_enabled=0
extended_power_menu=1
adbinstall=1
adbinput=1
# package name of the mock location app, or skip
mock_location_app=skip

# profile: fast | balanced | battery
profile=balanced
# log_level: 0 = errors only, 1 = normal, 2 = verbose
log_level=1
# engine: auto (react to changes) | poll (timed checks only)
engine=auto

Everything here is editable from the interface. A hand edit is picked up at once by the event engine. Windows line endings, extra spaces and # comments at the end of a line are all fine; a value that is not valid is ignored with a warning in the log, and the key is treated as skip.

skip is the value to use for a setting your device does not have. It is not the same as 0: 0 means "force it off", skip means "do not touch it at all".
7 · command line

Everything the interface does goes through service.sh, so you can do all of it from a root shell.

S=/data/adb/modules/dev-options-persist/service.sh

sh $S --status                  # config, live values, daemon state
sh $S --apply                   # enforce now
sh $S --restore                 # original values, pauses enforcement

sh $S --config adb_enabled 1    # 1 | 0 | skip
sh $S --config profile battery  # fast | balanced | battery
sh $S --config engine poll      # auto | poll
sh $S --config mock_location_app com.example.app   # or skip
sh $S --mock-apps               # apps offered in the picker
sh $S --config log_level 2      # 0 | 1 | 2

sh $S --daemon-start
sh $S --daemon-stop

sh $S --log 200
sh $S --clear-log

--status prints plain key=value lines, so it is easy to use in a script:

sh $S --status | grep -E '^(DRIFT|MODE|WATCHER_PID)='
sh $S --status | grep '^LIVE_adb_enabled='
8 · restore & uninstall

The installer snapshots every managed value before the module touches anything — including whether a setting existed at all and whether a property was set. A value managed by a newer version (like the mock location app after updating) is captured right before the module changes it for the first time.

Restore Original

Puts that snapshot back and pauses enforcement, because a running daemon would otherwise reapply your config within a second. Apply Now, Restart Daemon or a reboot resumes it.

Uninstall

Removing the module restores the snapshot automatically: settings that did not exist are deleted again and properties that were unset are cleared. Because uninstall.sh runs early in boot, before the settings service exists, the settings part is repeated once the service answers, and only then is the data directory removed.

Developer Options are always restored as visible, whatever the snapshot says. Hidden Developer Options is the one state you could not get out of once the module that hid them is gone.
9 · troubleshooting

The header says "poll engine" but Engine is auto

inotifyd is missing or kept exiting, and the daemon fell back on its own. The Engine card says which. Enforcement still works, just on a timer; the log has the reason.

Daemon shows as stopped

Press Apply Now — it restarts the daemon as well as enforcing. Check the log for why it exited. A daemon started from this interface moves itself out of the manager app's cgroups and pins oom_score_adj, so it behaves like a boot-started service.

Drift that never clears

The system refuses the value. The failure is logged once as an error together with the value that was actually read back, and retried on every later change.

The mock location app went back to "not managed"

The chosen app was uninstalled, so the choice was released (the log says so). Reinstall it and pick it again. A package that is not installed cannot be picked, and never takes the permission away from the current app.

My mock location app is not in the list

Only apps that ask for android.permission.ACCESS_MOCK_LOCATION can be selected — the same rule Settings uses. Some location spoofers work through LSPosed instead and do not need it.

extended_power_menu always drifts

That setting only exists on Xiaomi / HyperOS. Set it to skip.

"settings service not answering" in the log

The settings service did not respond. This is logged once, not on every retry, and clears on its own. During a reboot it is expected and not logged at all.

Interface is blank or shows a red box

Your root manager did not provide a working ksu JavaScript bridge. Open the module through KernelSU, SukiSU, APatch or MMRL.

10 · file layout
/data/adb/modules/dev-options-persist/
├── service.sh        boot flow, daemon, command interface
├── sh/common.sh      paths, key table, config, logging
├── customize.sh      installer, captures the original values
├── uninstall.sh      restores them
└── webroot/          this interface

/data/adb/dev-options-persist/     (mode 0700)
├── config            your settings
├── original          values from before installation
├── logs/service.log  rotates at 128 KB
└── run/              runtime only, cleared on boot
    ├── state         counters, engine, pids
    ├── daemon.pid
    ├── watcher.pid
    ├── events        FIFO between inotifyd and the daemon
    ├── mock-scan     per-app scan results (package, version, 0/1)
    └── mock-scan.stamp  packages.xml state the scan matches

Nothing mutable lives in the module directory, because a module update replaces it wholesale.
