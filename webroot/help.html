1 · what this module does

Turning Developer Options off in Android's Settings also turns off everything inside it — USB debugging goes with it. This module keeps the switches you care about in the state you chose, while Developer Options themselves stay hidden from the Settings menu.

The result: the developer menu is not visible, but ADB keeps working.

A background daemon watches for anything that changes those values — you, an app, an OTA, a settings reset — and puts them back.
2 · the five settings
settingwhere it lives
USB Debuggingglobal / adb_enabled
Developer Optionsglobal / development_settings_enabled
Extended Power Menusecure / extended_power_menu
Install via USBprop / persist.security.adbinstall
USB Debugging (Security)prop / persist.security.adbinput

The inverted one

Developer Options is the only toggle whose switch means hidden. Green means the menu is hidden from Settings — which is the point of the module. The runtime table shows the raw value, where 0 is hidden.

Xiaomi-specific

The last three exist on Xiaomi / HyperOS. On another manufacturer they either do nothing or never appear, and the runtime table will show a permanent drift. Set them to skip and the daemon will leave them alone.

3 · how enforcement works

Naively, a daemon like this polls every few seconds and re-reads everything. That is what earlier versions did, and it cost roughly a million process spawns per day — enough to keep the CPU from settling into deep sleep around the clock.

The mtime gate

Any change to an Android setting rewrites /data/system/users/0/settings_global.xml or settings_secure.xml. A single stat of those two files, plus the module's own config file, produces a fingerprint. If the fingerprint is unchanged, nothing could have changed, and the daemon does not query the settings provider at all.

An idle pass is four processes: sleep, one stat, and two getprop calls for the properties, which the settings databases do not cover.

Backoff

After a few quiet passes the interval stretches to the profile maximum, and it snaps back to the minimum the moment something changes.

Safety net

A full verification runs at least every few minutes regardless, in case a ROM writes settings somewhere the gate cannot see.

Idle cost in the balanced profile: about four process spawns per minute, and no write to module.prop unless the status text actually changes.
4 · poll profiles & battery
profileintervalfull check
fast5 → 15 severy 60 s
balanced15 → 60 severy 5 min
battery30 → 300 severy 15 min

Balanced is the default and is the right answer for almost everyone. The interval only decides how quickly a change is undone; it does not affect whether it is undone.

Pick fast if you are actively toggling things and want them corrected within seconds. Pick battery if the phone sits idle for long stretches.

A profile change does not restart the daemon. The config file is part of its fingerprint, so it picks up the new intervals on its own next pass — which on the battery profile can take up to five minutes.
5 · the interface

Status bar

  • enforcing — daemon alive, every managed value matches
  • drift detected — daemon alive, something does not match yet
  • daemon stopped — nothing is being enforced

Liveness is read from /proc/<pid>, so Doze and suspend cannot produce a false reading.

Runtime table

Per setting: what the config asks for, what the system actually reports, and whether they match. unmanaged means the key is set to skip.

Actions

  • Apply Now — enforce immediately, and restart the daemon if it is not running
  • Restart Daemon — stop and start it
  • Restore Original — put back the values captured when the module was installed
6 · configuration file

/data/adb/dev-options-persist/config — outside the module directory, so it survives module updates.

# 1 = force on, 0 = force off, skip = leave this setting alone
adb_enabled=1
development_settings_enabled=0
extended_power_menu=1
adbinstall=1
adbinput=1

# profile: fast | balanced | battery
profile=balanced
# log_level: 0 = errors only, 1 = normal, 2 = verbose
log_level=1

Everything here is editable from the interface. If you edit the file by hand instead, the daemon notices on its next pass — no restart needed.

skip is the value to use for a setting your device does not have. It is not the same as 0: 0 means "force it off", skip means "do not touch it at all".
7 · command line

Everything the interface does goes through service.sh, so you can do all of it from a root shell.

S=/data/adb/modules/dev-options-persist/service.sh

sh $S --status                  # config, live values, daemon state
sh $S --apply                   # enforce now
sh $S --restore                 # values captured at install time

sh $S --config adb_enabled 1    # 1 | 0 | skip
sh $S --config profile battery  # fast | balanced | battery
sh $S --config log_level 2      # 0 | 1 | 2

sh $S --daemon-start
sh $S --daemon-stop

sh $S --log 200
sh $S --clear-log

--status prints plain key=value lines, so it is easy to use in a script:

sh $S --status | grep '^DRIFT='
sh $S --status | grep '^LIVE_adb_enabled='
8 · restore & uninstall

The installer snapshots every managed value before the module touches anything. Removing the module restores that snapshot.

Developer Options are always restored as visible, whatever the snapshot says. Hidden Developer Options is the one state you cannot get out of once the module that hid them is gone.

Uninstall cleanup also runs again after sys.boot_completed, because uninstall.sh can execute long before system_server exists and a direct attempt would silently do nothing.

To check the result before committing, press Restore Original in the interface first.

9 · troubleshooting

Daemon shows as stopped

Press Apply Now — it restarts the daemon as well as enforcing. Check the log for why it exited.

A daemon started from this interface is a child of your root manager's shell, so it used to die whenever Android froze or killed the manager. It now moves itself into the root cgroup and pins oom_score_adj, which makes it behave like a boot-started service.

Drift that never clears

The live value refuses to accept the config value. Set the log level to verbose and press Apply Now — a failed write is logged as an error together with the value that was actually read back.

extended_power_menu always drifts

That setting only exists on Xiaomi / HyperOS. Set it to skip.

Interface is blank or shows a red box

Your root manager did not provide a working ksu JavaScript bridge. Open the module through KernelSU, SukiSU, APatch or MMRL.

The log warns that "settings" is unavailable

Nothing can be enforced without the settings command. This should never happen on a booted device.

10 · file layout
/data/adb/modules/dev-options-persist/
├── service.sh        boot flow, daemon, command interface
├── sh/common.sh      paths, logging, config, key table
├── customize.sh      installer, captures the original values
├── uninstall.sh      restores them
└── webroot/          this interface

/data/adb/dev-options-persist/     (mode 0700)
├── config            your settings
├── original          values from before installation
├── state             daemon pid, counters
├── daemon.pid
└── logs/service.log  rotates at 128 KB

Nothing mutable lives in the module directory, because a module update replaces it wholesale.
